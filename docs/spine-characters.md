# Базовые модели героя на Spine: этап 1, исследование

Отчёт агента от 09.11.2026 по заданию «Rift Warden: универсальная система 2D-персонажей и скелетной анимации». Это этап 1: исследование и выбор архитектуры. Код игры и игровые данные не менялись. Решения, без которых нельзя начинать этап 2 (графику), собраны в §9.

## 1. Коротко

- **Проект — Unity 6.6, C#.** Герой в полоске сейчас синий квадрат-заглушка. Spine и пакет 2D Animation в проекте не установлены. Своя пиксельная кукла v8 (`hero-look.md` §13–18) существует только как скрипты Python, которые запекают покадровые листы. В игру она не подключена.
- **spine2D-mcp редактором Spine не управляет.** Это генератор JSON из PSD с заглушками вместо предпросмотра. Под требования задания (100+ костей, меши, веса, скины, физика) он не подходит, ставить его не советую (§3).
- **Замена MCP проверена.** Агент пишет скелет Spine 4.3 в JSON сам и проверяет его в официальном рантайме `spine-webgl` 4.3.13 в Chromium без редактора: меш с весами на двух костях, IK с коленом и физика волос работают (§4).
- **Spine подходит к проекту.** Рантайм `spine-unity` 4.3 работает с Unity 6. Есть три условия: версия редактора и рантайма совпадают до минорной цифры; меши, веса, IK и физика есть только в Spine **Professional**; у кого-то в команде должна быть лицензия Spine (§5).
- **Главный конфликт — масштаб и стиль.** Герой в полоске ростом около 48 px (×2 на экране). При таком росте палец занимает 1 px, а деформация меша ломает пиксельную сетку. Предлагаю такой путь: рисуем и ригаем в 4× (≈ 200 px), а в игре выводим пикселями через рендер в низкое разрешение (§6). Это нужно утвердить вместе со стилем: референс dark fantasy или стиль Cainos из `hero-look.md` §18.

## 3. spine2D-mcp: что в нём на самом деле

Изучены README, `SPINE2D_INTEGRATION.md` и весь исходный код (1 492 строки; один коммит «fix: resolve Spine import errors»).

**Инструменты MCP (5 штук):** `import_psd`, `setup_character`, `generate_animation`, `preview_animation`, `export_animation`, плюс ресурс `spine2d://characters`.

**Как он работает:**
- С редактором Spine не связан. Он пишет файл JSON, который человек сам импортирует в Spine через «Import Data».
- Риг строится по ключевым словам в именах слоёв PSD (`hair`, `arm_left`, `foot_right`…). Получается не больше 17 костей: root, body, head, руки, кисти, ноги, стопы, волосы, глаза. Кость ставится в центр первого подходящего слоя.
- Мешей, весов, путей, физики и transform-ограничений нет. IK строится простой. Скин один, `default`.
- Анимации — около десяти готовых шаблонов (wave, jump и подобные) с подбором по словам в описании. Вызов OpenAI в коде закомментирован.
- `preview_animation` и экспорт в `png`/`gif` пишут в файл текст `"GIF output placeholder"`, а не картинку.
- Формат файла — Spine 4.1. Зависимости старые: `pillow==9.0.0`, `flask==2.0.1`, `openai==0.27.0`.

**В этом окружении** MCP не подключён: в `.mcp.json` проекта только UnityMCP, и тот сейчас недоступен (ECONNREFUSED). Spine Editor в облаке не установлен, поэтому его версию проверить нельзя.

**Вывод.** Требованиям задания MCP не отвечает: развитый скелет, меши, веса, скины по категориям и физика в нём не поддержаны, а предпросмотр не работает. Ставить его не советую. Если Сергей всё же захочет, установка такая: клонировать репозиторий, `pip install -r requirements.txt`, добавить в настройки Claude Code сервер `python src/main.py --storage ./storage`. Конфигурацию системы агент без согласия не менял.

## 4. Чем заменить MCP (проверено)

Формат JSON Spine открыт и описан, а официальный рантайм читает его без редактора. Конвейер такой:

1. **Агент пишет данные скелета скриптом:** кости, слоты, ограничения (IK, transform, physics), меши с весами, скины, анимации.
2. **Агент проверяет данные в официальном рантайме** `@esotericsoftware/spine-webgl` 4.3.13 в Chromium (Playwright уже стоит в облаке). Позы рендерятся в PNG: можно смотреть стыки, пустоты и растяжения на крайних углах. Это те же диагностические позы, что требуются в §14 задания.
3. **Spine Editor на ПК Сергея:** импорт JSON («Import Data»), ручная правка весов там, где скрипт ошибся, упаковка атласа и экспорт `.skel`. Всё это можно гонять скриптом через командную строку Spine (`Spine -i … -o … -e …`).

**Проба** (`art/heroes/spine/probe/`, результат `probe-result.png`): нога из двух костей, меш на 18 вершин с весами (бедро → голень с плавным переходом у колена), двухкостный IK со стопой-целью и `bendPositive: false`, кость волос с physics-ограничением, анимация «удар ногой» со сдвигом корня. Сначала проверено на 4.3.13, после решения Сергея — на 4.2.120: колено гнётся, меш идёт за костями без разрывов, волосы отстают при рывке до 23° и возвращаются с перехлёстом.

Подводные камни формата, найденные пробой:
- **4.2:** у каждого ограничения (IK, transform, path, physics) должно быть своё поле `order`, разное у всех. Редактор пишет его всегда. Без него рантайм ставит в очередь только первое ограничение с `order: 0`, а остальные молча не работают — так сначала «не работала» физика волос. Генератор скелета обязан нумеровать `order`.
- **4.2:** ограничения лежат в разделах `ik`, `transform`, `path`, `physics`; `drawSkeleton(skeleton, premultipliedAlpha)`.
- **4.3** (на будущее): ограничения в общем массиве `constraints` с полем `type`, флага premultiplied alpha у `drawSkeleton` нет.

Генератор MCP (формат 4.1) ни того, ни другого не учитывает.

Запуск пробы: `npm i`, затем `python3 make_probe.py`, `python3 -m http.server 8765` и `node shot.js`.

## 5. Spine в Unity: совместимость и интеграция

**Рантайм.** `spine-unity` 4.3 ставится в Unity 6 пакетом UPM по git-ссылке из репозитория `EsotericSoftware/spine-runtimes`, ветка 4.3. Правило Spine: major.minor редактора и рантайма должны совпадать. Экспорт из Spine 4.3.x — рантайм 4.3. Агент проверит это, когда Сергей назовёт версию своего редактора.

**Лицензия.**
- Рантайм бесплатен для команды, у которой есть лицензия Spine Editor (Spine Runtimes License).
- Essential (69 $) даёт только кости, слоты, обычные картинки, скины и события. Меши, веса, свободная деформация, IK, transform, path и physics-ограничения, клиппинг — только в **Professional (379 $)**.
- Почти всё в задании (§5, §6, §10) требует Professional.
- Раньше Сергей просил «бесплатный вариант» (`hero-look.md` §11). Покупку должен подтвердить он.

**Формат экспорта.**
- В игру идёт бинарный `.skel` (меньше и быстрее грузится), атлас `.atlas` и PNG.
- Исходник `.spine` и JSON-экспорт хранятся в репозитории (LFS) рядом с исходными картинками частей.
- Фильтр атласа: Nearest (пиксели). Premultiplied alpha — как в шейдере `Spine/Skeleton` с URP 2D.

**Загрузка.** Файлы лежат в `Assets/Game/Art/Characters/…`. `SkeletonDataAsset` создаётся импортёром spine-unity. Герой — компонент `SkeletonAnimation`: он сам считает кадр и не тянет Animator, поэтому дешевле. Заглушка в `BattleView` меняется на `HeroView` в `Game.Presentation`. `Game.Core` про Spine не знает.

**Синхронизация с логикой (10 Гц).**
- Ядро выдаёт события: удар, скилл, урон по герою, переход к врагу.
- `HeroView` переводит их в треки `AnimationState`:
  - трек 0 — стойка, ходьба, связка ударов;
  - трек 1 — верх тела поверх ног (каст, блок);
  - трек 2 — лицо (моргание, эмоции);
  - трек 3 — добавочное дыхание.
- Сопоставление «событие → имя анимации и скорость» лежит в JSON (`hero-anims.json`), а не в коде.
- Ссылки на `Animation` кэшируются при загрузке, поэтому в кадре нет поиска по строке и нет аллокаций.

**Экипировка.**
- Каждый предмет — свой скин Spine с именем по категории: `body/male`, `hair/ponytail_01`, `armor/chest/plate_03`, `weapon/sword_1h_01`.
- При смене снаряжения код собирает общий скин через `Skin.AddSkin`, а не в каждом кадре.
- Для меньшего числа draw call скин перепаковывается в один атлас: `GetRepackedSkin` в spine-unity.
- Редкость — смена цвета слота (tint и dark color) или своего вложения.

**Вторичная анимация.**
- Physics-ограничения Spine 4.2+ на волосах, плаще, полах, ремнях.
- `skeleton.physicsTranslate` передаёт рывок героя.
- Для фигур друзей и при скрытом окне: `Physics.pose` или реже обновлять скелет. В spine-unity обновление невидимых скелетов отключается (`UpdateTiming`, `updateWhenInvisible`), это держит бюджет 1% CPU.

**Общие анимации для мужской и женской моделей.** Анимации в Spine хранят повороты относительно позы покоя, а смещения прибавляются к ней. Поэтому, если у двух скелетов одинаковые имена и иерархия костей, один и тот же ключ даёт одинаковое движение даже при разных длинах костей. План:
- два скелета `hero_male` и `hero_female` с одним списком костей, но своими длинами и положениями (пропорции);
- библиотека анимаций пишется один раз;
- скрипт агента копирует её между скелетами по именам костей;
- анатомически разные анимации (стойка, ходьба, дыхание) переопределяются отдельно;
- будущие пропорции (крупный, худой, низкий) — новый «профиль тела» на тех же костях.

## 6. Масштаб и стиль: что нужно решить

Требования задания рассчитаны на крупного HD-героя: пальцы из трёх сегментов, веки, брови, деформация живота. Игра — пиксельная полоска:
- герой ≈ 48 px ростом, на экране ×2;
- кисть — 3–4 px, глаз — 2×3 px (`hero-look.md` §15).

При таком росте:
- три сегмента пальца — меньше пикселя каждый;
- поворот и деформация пиксельной картинки в рантайме дают «ломаные» и полупрозрачные пиксели. Именно поэтому кукла v8 поворачивает части через RotSprite и запекает кадры.

Варианты:

| Вариант | Как | Плюсы | Минусы |
| --- | --- | --- | --- |
| **А. HD-риг, пиксельный вывод** (рекомендую) | Части рисуются в 4× (рост ≈ 200 px), риг и меши полные. В игре герой рендерится в текстуру 1× (Pixel Perfect Camera URP 2D или своя RT с Nearest) и выводится ×2 | Пиксельная сетка общая с врагами, деформации чистые. Тот же риг крупно в окне героя (14е.7) и на экране выбора (14в.9): там видны пальцы и мимика | Мелкие детали (пальцы, веки) в полоске почти не видны; нужен шаг рендера в RT |
| Б. Пиксельный риг 1× | Части в размере полоски, меши минимальные, повороты на Nearest | Дешевле всего рисовать | Ломаные пиксели при поворотах, пальцы и мимика не читаются, для Spine Professional почти нет работы |
| В. HD-герой без пикселей | Рисованный герой ≈ 200–300 px, сглаживание | Вся мимика и деформация видны | Расходится со всеми пиксельными врагами и фонами |

Пальцы при варианте А:
- в скелете у каждого пальца три сегмента (крупный показ, хват оружия);
- в полоске кисть берётся из набора поз-вложений: кулак, хват, ладонь, указание, щепоть;
- аниматору не нужно крутить 15 костей ради кадра в 4 px.

**Стиль.** Приложенный референс («Dark Fantasy Heroes Vol. 1») — тёмное фэнтези: фигура около 60 px, чёрная обводка, насыщенные фиолетовый, красный и сталь, бо́льшая детализация брони. А Сергей 09.11.2026 утвердил свою куклу «точь-в-точь как у Cainos»: тёплая коричневая обводка, приглушённая палитра, 48–53 px (`hero-look.md` §18). Это два разных стиля. Нужен один, иначе риг придётся перерисовывать. Сам набор с референса покупной, агент берёт из него только приёмы, без пикселей.

## 7. Предлагаемая архитектура (после ответов из §9)

**Кости** (имена `snake_case`, сторона суффиксом `_l` / `_r`, контроллеры с приставкой `ctrl_`, крепления с `anchor_`):
- корпус: `root`, `ctrl_cog` (центр тяжести), `hips`, `pelvis`, `spine_lower`, `spine_mid`, `spine_upper`, `chest`, `ribcage`, `belly` (деформация живота), `breast_l/r` у женского скелета и `pec_l/r` у мужского (одно назначение, разные веса), `scapula_l/r`, `neck`, `head`, `jaw`;
- лицо: `eye_l/r`, `pupil_l/r` (взгляд), `lid_up_l/r`, `lid_low_l/r`, `brow_l/r` (две кости на бровь: внутренняя и внешняя часть), `nose`, `mouth`, `mouth_corner_l/r`, `lip_up`, `lip_low`, `hair_root`;
- рука (на сторону): `clavicle`, `shoulder`, `arm_upper`, `elbow` (корректор локтя), `forearm`, `forearm_twist` (вращение запястья без скручивания меша), `wrist`, `hand`, `palm`, пальцы `thumb_1…3`, `index_1…3`, `middle_1…3`, `ring_1…3`, `pinky_1…3`, крепления `anchor_hand`, `grip_hand`;
- нога (на сторону): `hip`, `leg_upper`, `knee` (корректор колена), `leg_lower`, `ankle`, `heel`, `foot`, `toe`;
- контроллеры: `ctrl_hand_ik`, `ctrl_elbow_pole`, `ctrl_foot_ik`, `ctrl_knee_pole`, `ctrl_head_look`, `ctrl_chest`, `ctrl_pelvis`;
- крепления: `anchor_back`, `anchor_hip_weapon_l/r`, `anchor_ear_l/r`, `anchor_neck`, `anchor_belt`, `anchor_backpack`, `anchor_wings`, `anchor_fx_hand_l/r`, `anchor_fx_head`;
- вторичное (цепочки с physics): `hair_front_1…3`, `hair_side_l/r_1…3`, `hair_back_1…4`, `cape_l/m/r_1…4`, `skirt_f/b/l/r_1…3`, `sleeve_l/r`, `belt_tail_1…3`.

Итого ≈ 150 костей. Цепочки волос, плаща и юбки — «скиновые» кости (`skin: true`): они включаются только со скином, которому нужны. С одним базовым телом активно около 95 костей.

**IK/FK.** IK рук и ног со смешиванием `mix` 0…1: ключ на `mix` и есть переключатель IK/FK в Spine. Полюс локтя и колена — через направление сгиба плюс transform-ограничение от кости `pole`. Хват двуручного оружия — IK второй руки на `grip_hand`.

**Слоты и порядок отрисовки** (сзади вперёд): дальние волосы и плащ → дальняя рука с оружием и щитом → дальняя нога → таз, корпус, грудь, броня корпуса → ближняя нога → голова, лицо, волосы спереди → ближняя рука → оружие в ближней руке → передние аксессуары и эффекты. Смена сторон — ключами порядка отрисовки в анимациях поворота. Каждый слот брони стоит над своей частью тела, поэтому предметы разных категорий не спорят за один слот.

**Скины:** `body/male`, `body/female`, `face/<вариант>`, `hair/<имя>`, `cloth/<слот>/<имя>`, `armor/<head|chest|hands|feet>/<материал>_<номер>`, `weapon/<тип>/<имя>`, `acc/<точка>/<имя>`. Правило: скин меняет только свои слоты, а связь «предмет → слоты» лежит в JSON.

**Лицо.**
- Глаза, веки и брови двигаются костями и мешами.
- Формы рта (покой, A, E, O, U, M, улыбка, оскал) и варианты глаз (открыт, полуприкрыт, закрыт, прищур) — сменные вложения в слотах `mouth` и `eye_l/r`. Новая эмоция — новый набор вложений и ключей на тех же костях.

**Структура в репозитории.** Без параллельного дерева «RiftWarden/…» из задания:
